# 回收站设计

状态：设计稿，未实现。

目标：在加入批量清理、重复照片删除等破坏性操作前，先把“删除”从永久删除改成可恢复的回收站流程。

## 1. 场景

用户在相册、照片查看器、重复图像检测里删除照片：

```text
删除照片
→ 从原相册移出
→ 原文件与 XMP 移入回收站
→ 相册索引不再显示
→ 通知“已移入回收站”
```

之后用户可以：

- 在左侧“回收站”查看；
- 恢复照片到原相册；
- 永久删除单张或全部；
- 清空回收站。

回收站中的文件不参与相册列表、搜索、AI 索引、重复检测、连拍折叠和统计中的相册照片数。

## 2. 磁盘布局

每个用户的数据根下都有独立的回收站：

```text
albums/<owner>/__recycle__/
  <entry_id>/
    entry.json
    payload/
      <original-file-name>
      <original-file-name>.xmp
```

示例：

```text
albums/daniel/__recycle__/
  01J8Y6H4X9K3M2Q7/
    entry.json
    payload/
      PANA1234.jpg
      PANA1234.jpg.xmp
```

设计要点：

- `<owner>` 是照片所属账号，不是执行删除操作的人；
- `entry_id` 由服务端生成，使用 UUID/ULID，不接受客户端路径；
- 一个 entry 对应一个文件；
- 原文件与 XMP 放在同一个 `payload/` 下，避免恢复时丢失 sidecar；
- 同一次批量删除生成多个 entry，可选 `batch_id` 用于界面分组；
- `__recycle__` 以 `__` 开头，现有 `is_user_visible_album_dir()` 已经会把它排除在相册列表之外；
- 但 AI 扫描、统计、文件浏览器等路径仍需要显式跳过，不能只依赖相册列表过滤。

### entry.json

```json
{
  "version": 1,
  "entry_id": "01J8Y6H4X9K3M2Q7",
  "owner": "daniel",
  "album": "trip",
  "original_path": "albums/trip/2026/04/PANA1234.jpg",
  "original_name": "PANA1234.jpg",
  "deleted_at_unix_ms": 1780000000000,
  "deleted_by": "daniel",
  "size_bytes": 12345678,
  "modified_unix_seconds": 1770000000,
  "content_signature": "12345678:1770000000",
  "kind": "photo",
  "has_xmp": true,
  "batch_id": "b-01J8..."
}
```

`original_path` 仅用于恢复和展示。所有文件操作都必须先按 `entry_id` 读取 metadata，再做路径校验，不能直接相信客户端传来的 `original_path`。

## 3. 左侧入口

在左侧主导航增加独立入口：

```text
仪表盘
相册
文件
回收站
...
```

或者放在相册分组下面：

```text
相册
  ...
回收站
```

建议使用**独立主导航项**，因为它不是相册。

界面要求：

- 显示回收站文件数量或大小；
- 当前账号自己的回收站；
- 只读共享用户不显示别人的回收站；
- 手机端作为导航抽屉中的一项；
- 空状态、加载中、失败、无权限四种状态都要有。

## 4. 回收站页面

顶部：

```text
回收站
共 12 项 · 128 MB
[恢复所选] [永久删除] [清空回收站]
```

列表项：

```text
[缩略图]  PANA1234.jpg
          原相册：trip / 2026-04
          删除时间：2026-05-01 14:22
          大小：12.3 MB
          [恢复] [永久删除]
```

支持：

- 单选/多选；
- 全选当前页；
- 按删除时间排序；
- 按原相册过滤；
- 预览原图；
- 下载原图；
- 恢复；
- 永久删除；
- 清空。

不把回收站文件重新塞进普通相册网格，避免与正常照片混淆。

## 5. 删除流程

### 5.1 普通照片删除

现有 `api_albums_delete_photos` 的语义从“永久删除”改为“移入回收站”：

```text
校验 can_delete
→ 校验路径在相册目录内
→ 生成 entry_id
→ 创建 __recycle__/<entry_id>/payload
→ rename 原文件到 payload
→ rename XMP 到 payload
→ 写入 entry.json
→ 从相册索引移除
→ 返回 moved_to_recycle
```

响应：

```json
{
  "deleted": 3,
  "recycled": 3,
  "entry_ids": ["...", "..."],
  "remaining": 42
}
```

前端提示：

```text
已移入回收站，可在左侧“回收站”恢复。
[撤销]
```

“撤销”实际调用批量恢复接口，而不是重新上传。

### 5.2 文件浏览器删除

文件浏览器可能删除非照片文件。建议：

- 相册内的图片/视频：默认回收；
- 非媒体文件：仍可永久删除，但必须明确确认；
- 不要用一个模糊的“删除”按钮同时承担两种语义。

如果第一版只做照片回收，文件浏览器删除可以暂时保持原行为，但界面文案必须写“永久删除”。

### 5.3 相册删除

`api_albums_delete` 当前直接删除整个相册目录。

第一阶段不建议改变相册删除语义，避免“删除相册”和“删除相册内全部照片”混淆。

第二阶段可以支持：

```text
删除相册
→ 相册内所有媒体生成回收站 entry
→ 删除相册元数据和空目录
```

但这需要单独确认，不应和普通照片删除共用默认行为。

### 5.4 AI/重复照片清理

重复检测、批量清理、连拍清理调用同一套删除接口，因此默认进入回收站。

清理任务不应直接调用 `remove_file`。

## 6. 恢复流程

```text
entry_id
→ 读取 entry.json
→ 校验当前用户对 owner 的恢复权限
→ 校验 original album 仍存在
→ 校验目标路径仍在 albums/<owner>/ 下
→ rename payload 文件回原路径
→ rename XMP 回原路径
→ 删除 entry 目录
→ 重建相册索引
→ 可选重建缩略图/AI 索引
```

### 冲突处理

如果原路径已经存在：

- 默认不覆盖；
- 返回 conflict；
- UI 提供：
  - 取消；
  - 恢复为副本，例如 `PANA1234 (restored 1).jpg`；
  - 选择其他相册。

第一版建议默认“恢复为副本”，避免覆盖用户后来上传的文件。

### 原相册不存在

如果原相册已经删除：

- 保留 entry；
- 提示用户选择目标相册；
- 或者恢复到 `albums/<owner>/Restored/` 新相册。

第一版建议要求用户选择目标相册，不自动创建。

### 恢复后的缓存

- 相册索引：必须重建；
- 缩略图：可以复用内容签名缓存，也可以重建；
- AI 索引：标记为需要重新扫描；
- 重复检测/连拍：下一次扫描时重新生成。

## 7. 永久删除

```text
永久删除 entry
→ 删除 entry 目录（payload + entry.json）
→ 不可恢复
```

必须：

- 二次确认；
- 显示文件数和大小；
- 明确写“永久删除，无法恢复”；
- 只允许 owner；
- 批量操作走任务系统，支持进度和失败列表；
- 清空回收站必须再次输入确认或使用强确认弹窗。

## 8. 权限

| 角色 | 删除到回收站 | 查看回收站 | 恢复 | 永久删除 |
| --- | --- | --- | --- | --- |
| 相册 owner | 可以 | 自己的 | 可以 | 可以 |
| 共享写/删用户 | 可以 | 否 | 否 | 否 |
| 共享只读 | 否 | 否 | 否 | 否 |
| 管理员 | 按当前账号 | 自己的 | 按权限 | 按权限 |

关键规则：

- 文件进入**照片 owner** 的回收站，不是执行删除者的回收站；
- `deleted_by` 记录执行者，用于审计；
- 共享用户删除后，照片从共享相册消失，但回收站由 owner 管理；
- 共享用户不能通过回收站接口读取 owner 的其他文件；
- 恢复时重新检查原相册的写权限。

## 9. 路径和 ID 安全

- 客户端只传 `entry_id` 或相册内相对路径；
- `entry_id` 必须是服务端生成的 UUID/ULID；
- 任何 `entry_id` 都不能拼进路径前先验证格式；
- 恢复目标路径必须经过 `into_host_path_safely`；
- 目标必须位于 `albums/<owner>/` 下；
- 不跟随符号链接；
- 响应和日志不输出绝对路径；
- 不允许通过 `entry.json` 的 `original_path` 恢复出数据根。

## 10. 排除规则

`__recycle__` 必须从以下位置排除：

- 左侧相册列表；
- 仪表盘统计；
- 文件浏览器相册树；
- AI 扫描；
- 重复检测；
- 连拍折叠；
- 相册搜索；
- WebDAV 相册浏览；
- 存储统计中的“相册”分类，单独计入“回收站”；
- 缩略图批量生成；
- 分享目标选择。

现有 `is_user_visible_album_dir()` 会隐藏 `__*`，但这条规则只覆盖相册列表，不能替代其他扫描入口的显式过滤。

## 11. 索引与缓存

删除时：

```text
原相册索引 → 移除条目
缩略图缓存 → 可保留，按内容签名失效
AI 索引 → 标记原相册需要重建
重复索引 → 旧索引失效
连拍缓存 → 旧缓存失效
```

恢复时：

```text
相册索引 → 重建
缩略图 → 需要时重生成
AI → 用户触发或按策略重扫
重复/连拍 → 下次扫描重建
```

回收站文件不进入 `AlbumIndex`，也不进入 AI 索引。

## 12. API 草案

```text
GET  /api/recycle?offset=0&limit=50
GET  /api/recycle/entry/{entry_id}
GET  /api/recycle/thumbnail/{entry_id}
GET  /api/recycle/file/{entry_id}
POST /api/recycle/restore
     { "entry_ids": ["..."], "conflict": "copy" }
POST /api/recycle/purge
     { "entry_ids": ["..."] }
POST /api/recycle/empty
```

所有接口：

- 需要会话；
- 只操作当前账号自己的回收站；
- 错误走现有 `AppError`；
- 批量操作创建任务并返回 `task_id`；
- 列表响应保持 `{ success, message, code, data }`。

## 13. 与存储分析的互动

回收站和存储分析必须使用同一套口径，否则用户会看到：

```text
删除了 3 GB 照片
→ 存储总量没有变化
→ 以为删除失败
```

这是正确的：文件只是从相册移到了回收站，仍然占磁盘。界面必须解释清楚。

### 13.1 分类口径

存储分析现有的分类是：

```text
相册
相册外
资源库
缓存（缩略图 / darktable 预览 / 转码 / AI）
```

增加：

```text
回收站
```

`albums/<owner>/__recycle__/` 不能继续算进：

- `albums`；
- `outside`；
- 未索引相册；
- 普通格式统计中的相册原片。

它应该单独计入 `recycle`，同时仍然计入用户的总占用，因为它确实占磁盘。

推荐：

```text
totals.bytes              # 包含回收站，代表实际占用
totals.albums             # 不含回收站
totals.outside            # 不含回收站
totals.recycle            # 新增
```

页面总览显示：

```text
总占用        15.2 GB
  相册        12.4 GB
  相册外       1.2 GB
  回收站       1.2 GB
  缓存         3.0 GB
```

“相册”和“回收站”分开，避免用户以为删除后空间立即释放。

### 13.2 删除、恢复、清空对数字的影响

| 操作 | 总占用 | 相册 | 回收站 |
| --- | --- | --- | --- |
| 删除照片到回收站 | 不变 | 减少 | 增加 |
| 从回收站恢复 | 不变 | 增加 | 减少 |
| 永久删除单张 | 减少 | 不变 | 减少 |
| 清空回收站 | 减少 | 不变 | 清零 |

重复照片清理、批量删除只在移动到回收站时改变分类，不释放磁盘。真正释放空间必须永久删除或清空。

因此：

- 删除成功的提示要写“已移入回收站，尚未释放空间”；
- 清理确认框要区分“移入回收站”和“永久删除”；
- “可释放空间”只在永久删除/清空时计算。

### 13.3 存储分析扫描

扫描数据根时：

```text
dist/data/{me}/
```

必须显式跳过：

```text
albums/__uploading/
albums/__recycle__/
```

不要把 `__recycle__` 当成：

- 相册；
- 未索引相册；
- 相册外目录；
- 普通原片格式统计的一部分。

单独遍历 `albums/<owner>/__recycle__/` 得到：

```json
"recycle": {
  "files": 12,
  "bytes": 1280000000
}
```

回收站内的文件格式可以继续计入总格式分布，但要带 `recycle` 来源，或至少在文档/界面说明它来自回收站，避免“为什么相册里没有这些 JPG，格式统计却有”。

### 13.4 存储分析页面

存储页需要：

- 总览增加“回收站”分类；
- 环形图增加回收站扇区；
- “按相册”表不把 `__recycle__` 列为相册；
- 回收站不提供普通相册的“建立索引”按钮；
- 回收站不能通过普通缓存清理接口删除；
- 回收站分类提供一个“打开回收站”的链接，而不是“清理”；
- 页面提示：

```text
回收站中的文件仍然占用磁盘，永久删除或清空后才会释放。
```

管理员成员视图：

- 成员的总占用包含该成员的回收站；
- 成员表可以增加回收站大小；
- 回收站属于成员自己的数据根，不因为共享相册转移。

### 13.5 与缓存清理的边界

回收站存的是原片和 XMP，不是缓存。

因此：

- `POST /api/storage/cleanup` 永远不能删除 `__recycle__/payload`；
- 存储清理只能处理缩略图、darktable 预览、转码等可重建缓存；
- 回收站的永久删除走 `/api/recycle/purge` 或 `/api/recycle/empty`；
- 清空回收站不应顺带清理其他账号的缓存。

### 13.6 缩略图和旧缓存

文件从：

```text
albums/trip/PANA1234.jpg
```

移动到：

```text
albums/trip/__recycle__/<entry_id>/payload/PANA1234.jpg
```

后，原来的缩略图 key 基于旧路径，通常会变成“未归属缩略图”。

设计上允许两种情况：

1. 移动时删除旧缩略图，回收站页面按需重新生成；
2. 保留旧缩略图，存储分析把它显示为未归属缓存，等清理任务回收。

第一版推荐：

- 不跟随文件移动旧缩略图；
- 回收站自己的缩略图按需生成；
- 旧缩略图计入“未归属缩略图”，存储页可以清理；
- 不要在移动时同时做一次昂贵的全量缩略图重算。

AI 索引同理：

- 原相册索引需要重建；
- 旧 AI/重复/连拍缓存可能失效；
- 这些属于可重建缓存，不能算进回收站原片大小；
- 回收站文件不进入 AI 扫描。

### 13.7 过期报告

存储报告是快照。删除到回收站、恢复或清空后：

- 报告可能过期；
- 页面显示“上一次统计时间”；
- 用户点击“重新统计”后再看到新分类；
- 不要在删除后立即同步全盘扫描，避免每次删除都触发重扫描。

### 13.8 测试

- 删除一张照片后总占用不变，`albums` 减少、`recycle` 增加；
- 恢复后总占用不变，`albums` 增加、`recycle` 减少；
- 永久删除后总占用减少；
- 清空回收站后 `recycle=0`；
- `__recycle__` 不出现在相册表和未索引相册里；
- 存储扫描不跟随 `__recycle__` 里的符号链接；
- 普通缓存清理不会删除回收站 payload；
- 回收站接口不会删除其他账号的缓存；
- 旧缩略图可以作为未归属缓存被清理；
- 共享相册文件的回收站大小归 owner，不归共享用户。

## 14. 保留策略

第一版不做自动清理。

后续可以增加：

```text
回收站保留时间：7 天 / 30 天 / 90 天 / 永不
```

自动清理必须：

- 只删除超过保留期的 entry；
- 有日志；
- 不删除正在恢复中的 entry；
- 默认为“永不自动删除”。

## 15. 实现顺序

### 阶段 1：基础设施

- `RecycleEntry` / `RecycleStore`；
- `__recycle__` 目录和 `entry.json`；
- 移动文件 + XMP；
- 排除规则；
- 单元测试。

### 阶段 2：删除改造

- `api_albums_delete_photos` 改为移入回收站；
- 删除响应增加 `entry_ids`；
- 原相册索引刷新；
- 前端提示和撤销。

### 阶段 3：回收站 UI

- 左侧入口；
- 列表、缩略图、原相册信息；
- 恢复；
- 永久删除；
- 空状态。

### 阶段 4：批量与任务

- 批量恢复；
- 批量永久删除；
- 清空；
- 任务进度和失败列表。

### 阶段 5：后续

- 相册删除回收；
- 保留策略；
- 跨账号管理员视图（如需要）。

## 16. 测试清单

- 删除图片后原文件不存在，回收站 payload 存在；
- XMP 随图片一起移动；
- 相册列表不再显示；
- 回收站列表显示原相册、时间、大小；
- 恢复后文件回到原路径；
- 恢复冲突时生成副本，不覆盖；
- 原相册不存在时拒绝或要求选择目标；
- 共享写用户删除进入 owner 回收站；
- 只读用户不能删除；
- 共享用户不能读取 owner 回收站；
- 带 `../` 的路径被拒绝；
- 伪造 `entry_id` 被拒绝；
- 永久删除后不可恢复；
- 清空回收站只删除自己的；
- `__recycle__` 不出现在相册、AI、重复、连拍、WebDAV 和统计中；
- 删除/恢复任务结束后进度为 100%。

## 17. 非目标

第一版不做：

- 文件版本历史；
- 回收站内编辑；
- 回收站分享；
- 跨用户管理员的统一回收站；
- 自动保留期清理；
- 相册整体删除回收。

这些都在普通照片删除闭环稳定之后再考虑。
